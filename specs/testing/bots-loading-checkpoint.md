# Bots loading checkpoint — 2026-10-11

## Behavior and ownership

Previously each Bots entry fetched the roster and then every avatar in sequence, refreshed content was cleared first, and selected-screen polling displayed loading/status labels. The current implementation separates metadata reads from image demand, retains content during refresh, shares bounded image caches, and polls screen controls silently.

- The repository keeps one in-memory roster scoped to the saved connection, canonical origin, socket generation, and cache invalidation epoch. A monotonic 60-second window suppresses repeated roster reads on warm entry. Expired metadata remains presentation-only while revalidation runs; automatic favourites and different-bot selection wait for acceptance. Explicit refresh bypasses freshness and concurrent refreshes are deduplicated. Accepted empty results replace retained rows.
- Compose reports selected and visible favourite/picker names. Three repository-owned avatar reads run concurrently, queued in that order. Matching reads are deduplicated; removed visibility and page exit cancel work. Cancellation is not cached as failure. Failed reads do not remove usable roster metadata or affect other images.
- The encoded-image LRU is 8 MiB; the decoded-thumbnail LRU is 4 MiB, measured from production bitmap allocation size. Active visible references are outside cache budgets. Thumbnails retain the existing 160-pixel decode target; digesting and decoding run off the main thread. A remaining visible consumer can recover when a different presentation cancels the shared decode.
- The asset contract has no version, so each accepted roster refresh revalidates demanded avatars while retaining old images until replacement. Removed/disabled avatars are pruned. Missing/invalid images keep initial-letter fallbacks. No protocol, persistence format, migration, host infrastructure, or remote history changes are introduced. Conversation-preview caching is excluded.
- Matching conversation rows and their count remain visible during list refresh; the existing ready/scope guards still disable opening and sending until loading completes. Unscoped or recovered fallback lists remain hidden.
- Favourites remain encrypted local preferences. Their credential-bearing owner is read on entry/refresh, cleared on exit, and never retained in the application cache. Refresh failures retain favourite names but disable saving when current ownership is unavailable. Refresh does not repeat initial favourite selection.
- Disconnect/reset clears caches, cancels page-owned jobs, and advances synchronous admission epochs. Explicit sign-out/profile teardown blocks the previous socket generation even before transport closure. Late non-cooperative roster, avatar, decode, and status completions cannot restore old presentation.
- Bots displays no passive screen-status labels, polling spinners, or changing action labels. Open remains an action; Stop requires an installed, supported, running, bot-held screen and is disabled during reads/writes. Polling reads immediately on selection/resume, then waits 15 seconds after running results or 60 seconds otherwise. Background cancels reads. A confirmed stop sends one write and one reconciliation read; unconfirmed outcomes appear only in a dialog after the requested action, with no automatic resend.
