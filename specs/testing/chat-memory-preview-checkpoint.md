## Behavior and decisions

The keyed chat ViewModel still clears on route exit, cancelling its collectors and owned reads. The application-scoped preview repository retains only sanitized immutable host-history presentation, up to four entries / 4 MiB serialized payload, LRU eviction, and the existing seven-day expiry. A warm owner-bound preview seeds a new ViewModel synchronously before its first render; this path performs no vault IO. A cold encrypted preview starts as a sibling before history-scope preparation and does not await REST/WebSocket auth preparation. Sync still runs on every connected open. Late cache results cannot replace accepted host publication; failed sync preserves a valid preview. A small Syncing label accompanies read-only preview rows.

The vault's process-local authority gate linearizes memory publication with ownership revocation. Lock order is vault mutex, authority gate, repository memory lock; no IO or suspension belongs inside the short gate. Capture establishes authority only after authoritative selection and partition validation. Account/login, sign-out, profile/origin/workspace, deletion, cache purge/reset and failed ownership mutations revoke before IO, releasing memory entries. Normal cookie renewal preserves preview authority only when the existing local-login partition remains stable. Detected unreadable selection or failed capture closes the gate. Unsupported storage implementations fail closed. Tokens and generations remain opaque, process-local, redacted and unserialized.

Only accepted host projections and validated encrypted snapshots populate memory. REST history remains a display projection: it is never converted into compact cache messages or written to the encrypted snapshot schema. Pending/interim/optimistic rows, unfinished streams, runtime handles, editable targets, approvals, local drafts and raw tool payloads never enter preview memory. Tool previews retain completed names only. Fast memory retention at host publication reuses current local authority before ancillary disk writes; persistence failures do not erase memory availability. No protocol, persistence schema, migration, retention, Keystore, backup, submission or retry policy change.
